## 2. TCP 消息一览

| message_id | 名称                              | 方向            | 说明                |
|------------|-----------------------------------|-----------------|---------------------|
| `1033`     | `MESSAGE_GROUP_CREATE_REQ`        | 客户端 → 服务端 | 创建群聊            |
| `1034`     | `MESSAGE_GROUP_CREATE_RSP`        | 服务端 → 客户端 | 创建回包（含群 id） |
| `1035`     | `MESSAGE_GROUP_ADD_MEMBERS_REQ`   | 客户端 → 服务端 | 拉人入群            |
| `1036`     | `MESSAGE_GROUP_ADD_MEMBERS_RSP`   | 服务端 → 客户端 | 拉人回包            |
| `1037`     | `MESSAGE_GROUP_KICK_MEMBER_REQ`   | 客户端 → 服务端 | 踢人                |
| `1038`     | `MESSAGE_GROUP_KICK_MEMBER_RSP`   | 服务端 → 客户端 | 踢人回包            |
| `1039`     | `MESSAGE_GROUP_DISMISS_REQ`       | 客户端 → 服务端 | 解散群聊            |
| `1040`     | `MESSAGE_GROUP_DISMISS_RSP`       | 服务端 → 客户端 | 解散回包            |
| `1041`     | `MESSAGE_GET_GROUP_USER_INFO_REQ` | 客户端 → 服务端 | 获取群成员信息      |
| `1042`     | `MESSAGE_GET_GROUP_USER_INFO_RSP` | 服务端 → 客户端 | 群成员信息回包      |

> 群消息本身继续使用 `1013` / `1014` / `1022` / `1023` / `1024` / `1025` / `1026`，见 §9。
> 帧格式见 [`api-tcp.md`](api-tcp.md)：`[message_id:2][body_len:2][body]`。
> 本组所有处理器都使用 `HANDLER_PREFIX`：未登录（`session->getUserId() == 0`）直接返回 `1011`，并统一回显 `msgid`。

## 3. 数据与权限模型

### 3.1 存储

| 层    | key / 表                                                      | 说明                                                                 |
|-------|---------------------------------------------------------------|----------------------------------------------------------------------|
| MySQL | 群基础信息（表名不在本仓库，代码只通过存储过程访问）          | 群 id、群名、头像、公告、群主、最大人数                              |
| MySQL | `group_members(group_id, user_id, role, nickname, joined_at)` | 群成员与角色，`role` 为 `owner` / `admin` / 其它（一律视为普通成员） |
| Redis | `chatgroup_<group_id>`（Set）                                 | 成员 uid 的十进制字符串集合；`SISMEMBER` 校验、`SMEMBERS` 取成员     |
| Redis | `offlinestream_<uid>`（Stream）                               | 群消息按成员逐个投递到各自的离线流，字段带 `group=y`（§9.2）         |

- `chatgroup_<group_id>` **没有 TTL**，也没有登录重建逻辑；只有「创建群聊」（写群主）、「拉人成功」（追加成员）、「踢人成功」（`SREM`
  ）、「解散成功」（`DEL`）会改动它。
- 解散成功后的 `DEL` 用请求体 `group_id` 原串拼 key（见 §7.3）；`RedisManager::removeGroup` 仍没有任何调用方。
- 群消息 **不再使用** `offlinestream_group_<gid>`，该宏已注释废弃。

### 3.2 角色与权限

| 值 | 含义     | 说明                                             |
|----|----------|--------------------------------------------------|
| 2  | 群主     | 只有群主能解散群聊                               |
| 1  | 管理员   | 可拉人、可踢人（不能踢群主，管理员之间不能互踢） |
| 0  | 普通成员 | 可发群消息、可拉取群成员信息                     |

- 权限最终由存储过程判定（`add_group_member` / `kick_group_member` / `dismiss_group` 返回负值），服务端只做错误码映射。
- 服务端 **不校验** 操作人角色，完全信任存储过程。

## 4. 创建群聊（1033 / 1034）

### 4.1 请求 `MESSAGE_GROUP_CREATE_REQ`（1033）

```json
{
  "msgid": "c-1001",
  "name": "产品交流群",
  "avator": "http://example.com/group.png",
  "announcement": "禁止广告"
}
```

| 字段           | 类型   | 必填 | 说明                                                         |
|----------------|--------|------|--------------------------------------------------------------|
| `msgid`        | 任意   | 否   | 请求级唯一编号（所有接口通用），服务端原样回显               |
| `name`         | string | 是   | 群名称；缺失按空串处理，**不校验长度与内容**                 |
| `avator`       | string | 否   | 群头像 URL；**字段名拼写为 `avator`**，服务端不识别 `avatar` |
| `announcement` | string | 否   | 群公告                                                       |

- 群主固定为当前会话 uid（`session->getUserId()`），请求体不传。
- `max_members` 由服务端固定为 **500**，客户端不能指定。
- 落库：`Mysql_boost::createChatGroup` → `CALL create_group(name, avator, uid, 500, announcement, @result, @error)`。
- Redis：成功后把 **群主** 写入 `chatgroup_<gid>`；其它初始成员（若存储过程额外写入）不会同步到 Redis。
- 成功后会以 **系统账号 `uid = 1`** 向该群写入一条系统消息：`群聊 <group_id> 已创建`，随后通过 `notifyMessageSend` 推送
  `1022`（此时成员只有群主，见 §9.5）。

### 4.2 响应 `MESSAGE_GROUP_CREATE_RSP`（1034）

```json
{
  "error": 0,
  "msgid": "c-1001",
  "group_id": "20001"
}
```

| 字段       | 类型   | 说明                          |
|------------|--------|-------------------------------|
| `error`    | int    | 见下表                        |
| `msgid`    | 任意   | 原样回显                      |
| `group_id` | string | 新建群 id；失败时不出现该字段 |

| error  | 含义                                        | 来源                       |
|--------|---------------------------------------------|----------------------------|
| `0`    | 创建成功                                    | 存储过程 `@error = 0`      |
| `1011` | 会话未登录，或存储过程表示 uid 不存在       | 宏前置校验 / `@error = -1` |
| `1013` | 数据库不可用（连接失败、`@error` 其它负值） | `-10` / `-11` / 其它       |

- Redis 写入失败时异常会逃逸出处理器，回包只有 `msgid`、 **没有 `error` 字段**（也不会返回 `group_id`）。

## 5. 拉人入群（1035 / 1036）

### 5.1 请求 `MESSAGE_GROUP_ADD_MEMBERS_REQ`（1035）

```json
{
  "msgid": "c-1002",
  "group_id": "20001",
  "members": ["10002", "10003"]
}
```

| 字段       | 类型            | 必填 | 说明                                     |
|------------|-----------------|------|------------------------------------------|
| `msgid`    | 任意            | 否   | 原样回显                                 |
| `group_id` | string          | 是   | 群 id，纯数字字符串，解析失败返回 `1020` |
| `members`  | array\<string\> | 是   | 待加入成员 uid 列表；不是数组返回 `1020` |

- 只做"拉人"， **不校验** 被邀请者是否存在、是否好友、是否在线；没有邀请确认流程，被邀请者通过系统消息的 `1022` 通知感知（在线时）。
- 逐个调用 `add_group_member(group_id, uid, operator_id)`；返回 `-3`（已在群内）时跳过并继续，其它负值立即结束。
- 全部处理成功后把本次新增的 uid 追加到 `chatgroup_<gid>`；已在群内的成员不会重复添加。
- 随后以系统账号 `uid = 1` 向该群写入一条系统消息：`邀请了 <N> 个好友`（`N` 为本次成功新增的人数，§9.5）；因为先写 Redis
  集合再发消息， **新成员也能收到**。

### 5.2 响应 `MESSAGE_GROUP_ADD_MEMBERS_RSP`（1036）

```json
{
  "error": 0,
  "msgid": "c-1002"
}
```

| error  | 含义                                       | 存储过程返回 |
|--------|--------------------------------------------|--------------|
| `0`    | 处理完成，且本次至少新增了 1 名成员        | `0`          |
| `1011` | 会话未登录                                 | ——           |
| `1020` | `group_id` 解析失败，或 `members` 不是数组 | ——           |
| `1023` | `GROUP_ID_INVALID`：群不存在               | `-1`         |
| `1024` | `NO_POWER`：操作人不是群主 / 管理员        | `-2`         |
| `1013` | 数据库不可用，**或群人数已满**             | `-4` / 其它  |

- 群已满（`-4`） **没有**映射到 `1025 GROUP_FULLED`（该错误码已定义但未使用），客户端只能看到 `1013`。
- 若所有成员都已在群内（`-3` 全部跳过）或 `members` 是空数组，`added_members` 为空仍会执行无参数的
  `SADD chatgroup_<gid>`，Redis 报错并抛异常 → 回包只有 `msgid`、 **没有 `error` 字段**（§11.9）。
- 响应不回传实际入群名单；客户端需重新拉取群成员信息（`1041`）确认。

### 5.3 一致性

- 逐成员独立提交， **没有整体事务**：中途失败时，之前成功的成员已经在 MySQL 里入群。
- 只有全部成员处理完才写 Redis；中途失败时，本次已入群的成员在 `chatgroup_<gid>` 中缺失，且没有重建机制，只能重新调用本接口补齐。

## 6. 踢人（1037 / 1038）

### 6.1 请求 `MESSAGE_GROUP_KICK_MEMBER_REQ`（1037）

```json
{
  "msgid": "c-1003",
  "group_id": "20001",
  "uid": "10002"
}
```

| 字段       | 类型   | 必填 | 说明                              |
|------------|--------|------|-----------------------------------|
| `msgid`    | 任意   | 否   | 原样回显                          |
| `group_id` | string | 是   | 群 id，解析失败返回 `1020`        |
| `uid`      | string | 是   | 被踢成员 uid，解析失败返回 `1020` |

- 操作人取会话 uid；被踢者必须是同群成员。
- 成功后先以系统账号 `uid = 1` 向群写入系统消息：`踢出了 <uid>`，调用 `notifyMessageSend` 推送 `1022`，再执行
  `SREM chatgroup_<gid> <uid>`（§9.5）。
- 因为发消息和通知时被踢者仍在成员集合内， **被踢者本人也会收到这条系统消息的 `1022`**，离线流里也有这条消息；之后才被移出群。
- 不清理被踢者离线流中已入队的群消息。

### 6.2 响应 `MESSAGE_GROUP_KICK_MEMBER_RSP`（1038）

```json
{
  "error": 0,
  "msgid": "c-1003"
}
```

| error  | 含义                                                 | 存储过程返回       |
|--------|------------------------------------------------------|--------------------|
| `0`    | 踢出成功                                             | `0`                |
| `1011` | 会话未登录                                           | ——                 |
| `1020` | `group_id` / `uid` 解析失败                          | ——                 |
| `1023` | 群不存在                                             | `-1`               |
| `1024` | 无权限：不能踢群主 / 操作人权限不足 / 管理员不能互踢 | `-2` / `-4` / `-5` |
| `1014` | 被踢者不在群内（`USER_NOT_FOUND` 被复用）            | `-3`               |
| `1013` | 数据库不可用                                         | 其它负值           |

- `1014` 的语义在单聊中是"查询的用户不存在"，这里表示"目标用户不在群内"。
- Redis `SREM` 失败会抛异常并逃逸出处理器（回包缺少 `error`），此时 MySQL 已经踢出（弱一致）。

## 7. 解散群聊（1039 / 1040）

### 7.1 请求 `MESSAGE_GROUP_DISMISS_REQ`（1039）

```json
{
  "msgid": "c-1004",
  "group_id": "20001"
}
```

| 字段       | 类型   | 必填 | 说明     |
|------------|--------|------|----------|
| `msgid`    | 任意   | 否   | 原样回显 |
| `group_id` | string | 是   | 群 id    |

- 仅群主可解散，由存储过程 `dismiss_group` 判定。
- 成功后先以系统账号 `uid = 1` 写入 `该群聊已解散` 并调用 `notifyMessageSend` 推送 `1022`（此时成员集合还在，
  **所有在线成员都会收到**），再 `DEL chatgroup_<gid>`（§9.5）。

### 7.2 响应 `MESSAGE_GROUP_DISMISS_RSP`（1040）

```json
{
  "error": 0,
  "msgid": "c-1004"
}
```

| error  | 含义                           | 存储过程返回           |
|--------|--------------------------------|------------------------|
| `0`    | 解散成功                       | `0`                    |
| `1011` | 会话未登录                     | ——                     |
| `1020` | `group_id` 解析失败            | ——                     |
| `1024` | 操作人不是群主                 | `-2`                   |
| `1013` | 数据库不可用，**以及群不存在** | `-1` / 其它（见 §7.3） |

### 7.3 ⚠️ 当前实现问题

1. **群不存在返回 `1013` 而不是 `1023`**：代码是 `if (result == -1) {...} if (result == -2) {...} else {...}`，`-1` 先把
   `error` 置为 `1023`，随后第二个 `if` 的 `else` 分支又覆盖为 `1013`。
2. **Redis 清理用请求原串拼 key**：MySQL 解散成功后执行 `DEL chatgroup_<root["group_id"].asString()>`：
    - `group_id` 带前导零（如 `020001`）时，解析成功但删的是 `chatgroup_020001`，真实 key `chatgroup_20001` 残留；
    - `DEL` 失败（Redis 不可用）会抛异常并逃逸出处理器 → 回包缺少 `error`，但 MySQL 已解散，且系统消息已经写入；
    - 不清理各成员离线流中已入队的群消息。

## 8. 获取群成员信息（1041 / 1042）

### 8.1 请求 `MESSAGE_GET_GROUP_USER_INFO_REQ`（1041）

```json
{
  "msgid": "c-1005",
  "gid": "20001"
}
```

| 字段    | 类型   | 必填 | 说明                                                          |
|---------|--------|------|---------------------------------------------------------------|
| `msgid` | 任意   | 否   | 原样回显                                                      |
| `gid`   | string | 是   | 群 id；**字段名是 `gid`**，与本组其它接口的 `group_id` 不一致 |

### 8.2 响应 `MESSAGE_GET_GROUP_USER_INFO_RSP`（1042）

```json
{
  "error": 0,
  "msgid": "c-1005",
  "mb_infos": [
    { "nick_g": "群主昵称", "join_at": "1734567890123", "uid": "10001", "role": 2 },
    { "nick_g": "", "join_at": "1734567899999", "uid": "10002", "role": 0 }
  ]
}
```

| 字段                 | 类型   | 说明                                                                       |
|----------------------|--------|----------------------------------------------------------------------------|
| `error`              | int    | `0` 成功；`1020` `gid` 解析失败；`1024` 不在群内；`1013` 数据库不可用      |
| `msgid`              | 任意   | 原样回显                                                                   |
| `mb_infos`           | array  | 成员列表；**没有成员时不出现该字段**                                       |
| `mb_infos[].nick_g`  | string | 群内昵称（`group_members.nickname`，数据库为 `NULL` 时为空串），不是账号名 |
| `mb_infos[].join_at` | string | 入群时间，**毫秒时间戳字符串**                                             |
| `mb_infos[].uid`     | string | 成员 uid                                                                   |
| `mb_infos[].role`    | number | `0` 成员 / `1` 管理员 / `2` 群主                                           |

- 先校验 Redis `SISMEMBER chatgroup_<gid> <自己>`：不在群 → `1024 NO_POWER`。 **Redis key 不存在时同样返回 `1024`**
  （即使该用户是真实群成员）。
- 再查 MySQL `group_members`；查询结果为空 → `error = 1013`（代码假设"过了 Redis
  校验群一定存在"，实际会出现"集合存在但数据库无成员"的场景）。
- 不做权限区分：任何群成员都能拉取完整名单；无分页、无排序保证。
- 只返回群内昵称 / 入群时间 / uid / 角色；用户名、头像、性别等资料需按 `uid` 另查（见 [`api-friend.md`](api-friend.md)
  的用户搜索）。

## 9. 群消息（复用 1013 / 1022 / 1023 / 1024）

### 9.1 发送（1013 / 1014）

```json
{
  "msgid": "c-1006",
  "msg_id": "m-0001",
  "to_uid": "20001",
  "type": "1",
  "body": "大家好",
  "group": true
}
```

| 字段     | 类型   | 必填 | 说明                                                                                      |
|----------|--------|------|-------------------------------------------------------------------------------------------|
| `msgid`  | 任意   | 否   | 原样回显                                                                                  |
| `msg_id` | string | 是   | 客户端消息编号，回执原样回显                                                              |
| `to_uid` | string | 是   | **群 id**（不是成员 uid）                                                                 |
| `type`   | string | 是   | `1` 文本 / `2` 图片 / `3` 文件 / `4` 表情包                                               |
| `body`   | string | 是   | 消息内容                                                                                  |
| `group`  | bool   | 否   | `true` 表示群消息；缺省 `false` 走单聊。`asBool()` 对非空字符串也返回真，请传 JSON 布尔值 |

- 群聊 **不再校验好友关系**，改为 `SISMEMBER chatgroup_<gid> <from_uid>`；不在群（含 Redis 集合不存在）→ `1014` 返回
  `1022 NOT_FRIEND`（错误码复用）。
- 服务端 **不校验群是否存在**，只认 Redis 集合：群已被解散但 `chatgroup_<gid>` 未清理时仍能发送成功。
- 回执与单聊一致：`{"error":0,"msgid":"...","msg_id":"m-0001"}`，`0` 只代表已写入成员的离线流。

### 9.2 投递

- `RedisManager::insertMessageToOffline` 对 `SMEMBERS chatgroup_<gid>` 中的 **每个成员（含发送者本人）** 执行
  `XADD offlinestream_<member_uid>`，一次 pipeline 批量写（`streamsAdd`）。
- Stream 字段：`group = "y"`、`group_id`（群 id）、`from_uid`、`type`、`body`。
- 与单聊一致：无论成员是否在线都会写入；保留约 7 天；ACK 后删除。
- 发送者也会收到自己发的群消息（发送者本身也是群成员）。

### 9.3 通知（1022）

通知统一由 `LogicSystem::notifyMessageSend(is_group, to_id)` 完成：

- 单聊：按接收方 uid 查 `uip_<uid>`，本实例直接推送，跨实例走 gRPC `ChatService.NotifyChatMessage`。
- 群聊：`SMEMBERS chatgroup_<gid>` 取全部成员，逐个查 `uip_<uid>` 推送（本实例）或 gRPC 转发（跨实例）。
- 群聊遍历的所有分支都是 `continue`：成员离线、本实例无会话都只跳过当前成员， **不会再中断后续成员**。
- 通知体为空壳 `{"error":0}`，不含群 id、发送者或内容（与单聊一致）。
- 群聊中发送者本人也在成员集合内，因此 **发送者也会收到自己这条消息的 `1022`**。
- 调用时机：
    - 普通单聊 / 群聊消息写入消息流之后；
    - 创建群聊、拉人入群、踢人成功后的系统消息写入之后（踢人时通知发生在 `SREM` 之前，被踢者也能收到）；
    - 解散：系统消息写入后、`DEL` 群集合之前调用通知 → 成员列表还在， **所有在线成员都会收到 `1022`**。

### 9.4 拉取（1023 / 1024）

群消息与单聊消息共用同一条消费流 `offlinestream_<uid>`，`1024` 的每个群消息元素新增 `group` 与 `group_id`：

```json
{
  "error": 0,
  "count": 1,
  "msgs": [
    {
      "group": true,
      "group_id": "20001",
      "type": 1,
      "from_uid": "10002",
      "body": "大家好",
      "id": "1734567890123-0"
    }
  ]
}
```

| 字段              | 类型   | 说明                                        |
|-------------------|--------|---------------------------------------------|
| `msgs[].group`    | bool   | `true` 群消息 / `false` 单聊                |
| `msgs[].group_id` | string | 群 id；**仅群消息出现**（单聊不返回该字段） |
| `msgs[].type`     | number | 消息类型 `1`–`4`                            |
| `msgs[].from_uid` | string | 发送方 uid                                  |
| `msgs[].body`     | string | 消息内容                                    |
| `msgs[].id`       | string | Redis Stream 消息编号，ACK 时使用           |

- 群 id 在写入 `offlinestream_<uid>` 时以 `group_id` 字段保存，拉取时回填到 `msgs[].group_id`，客户端据此把消息归属到对应群。
- **升级前已入队的群消息**没有 `group_id` 字段（当时未写入），这类历史消息不会返回 `group_id`，客户端需按缺失处理。
- 拉取 / ACK 规则（PEL 优先、单次上限 10 条、ACK 即删除、`XACKDEL` 需 Redis 8.2+）与单聊完全一致，见 [
  `api-chat.md`](api-chat.md) §6–§7。

### 9.5 系统消息（`from_uid = 1`）

群操作成功后，服务端会以 **系统账号 `uid = 1`** 向群内写入一条文本消息，格式与普通群消息完全一致：

| 触发                 | `body`              | 写入时机（相对 Redis 操作）   | 消息流接收方               | `1022` 推送                  |
|----------------------|---------------------|-------------------------------|----------------------------|------------------------------|
| 创建群聊 `1033` 成功 | `群聊 <gid> 已创建` | 群主写入 `chatgroup_<gid>` 后 | 群主                       | 是（群主在线时）             |
| 拉人入群 `1035` 成功 | `邀请了 <N> 个好友` | 新增成员写入集合后            | 所有群成员（**含新成员**） | 是（所有在线成员）           |
| 踢人 `1037` 成功     | `踢出了 <uid>`      | 被踢者 `SREM` 之前            | 所有群成员（**含被踢者**） | 是（所有在线成员，含被踢者） |
| 解散 `1039` 成功     | `该群聊已解散`      | `DEL chatgroup_<gid>` 之前    | 所有群成员                 | 是（所有在线成员）           |

- Stream 字段：`group=y`、`group_id=<gid>`、`from_uid=1`、`type=1`、`body=<上表>`。
- `1024` 中的样子：`{"group":true,"group_id":"20001","type":1,"from_uid":"1","body":"群聊 20001 已创建","id":"..."}`；
  没有独立的“系统消息”标记，客户端按 `from_uid == "1"` 识别。
- 系统消息写入后都会调用 `notifyMessageSend` 推送 `1022`；解散在 `DEL` 之前通知，所有在线成员都能收到。
- 依赖约定： **uid `1` 保留给系统账号**，注册流程不能把 1 分配给真实用户；当前服务端没有强制校验，需数据库侧保证。
- 系统消息与普通群消息一样写入各成员的 `offlinestream_<uid>`，随 `1025` ACK 删除。

## 10. Redis 键位

| 键                     | 类型   | TTL                | 写入方     | 用途                                                           |
|------------------------|--------|--------------------|------------|----------------------------------------------------------------|
| `chatgroup_<group_id>` | set    | 无                 | ChatServer | 群成员 uid 集合；创建写群主、拉人追加、踢人 `SREM`、解散 `DEL` |
| `offlinestream_<uid>`  | stream | 约 7 天（`MINID`） | ChatServer | 群消息按成员逐个写入，字段 `group=y`、`group_id=<gid>`         |

- `offlinestream_group_<gid>` 已废弃（宏被注释），不要再用。
- 群成员集合没有 TTL 与重建逻辑：Redis 被清空 / 重启丢数据后，`isInGroup` 全部为假 → 群消息发送、成员信息查询全部失败。恢复只能靠重新执行拉人（
  `1035`）或手动补数据。

## 11. 已知问题与限制

1. **拉人非事务**（§5.3）：逐成员提交，中途失败不回滚，也不会写 Redis。
2. **解散错误码被覆盖**（§7.3）：群不存在时返回 `1013` 而不是 `1023`。
3. **解散清理 key 用请求原串**（§7.3）：带前导零等写法会漏删真实 key；`DEL` 失败时回包缺 `error`（MySQL 已解散）。
4. **`GROUP_FULLED`（`1025`）未使用**：群满（`-4`）在拉人接口被映射为 `1013 SERVICE_UNAVAILABLE`。
5. **字段命名不一致**：创建群用 `avator`（拼写错误）、成员查询用 `gid`，其余接口用 `group_id`。
6. **缺少基础能力**：主动退群、群列表、群资料修改、设置管理员、入群验证 / 邀请确认均未实现；被拉入群的用户只能通过系统消息的
   `1022` 感知。
7. **群人数上限硬编码 500**，客户端不可配置。
8. **Redis 与 MySQL 弱一致**：先 MySQL 后 Redis，Redis 失败不回滚；群集合无 TTL、无重建。
9. **空成员列表触发 Redis 异常**：拉人时若本次没有任何新增成员（全部已在群内），仍会用空数组调用 `SADD chatgroup_<gid>`
   ，Redis 返回参数错误并抛异常 → 回包只有 `msgid`、 **没有 `error` 字段**。
10. **创建群只同步群主到 Redis**：若存储过程还写入了其它初始成员，Redis 集合不会包含他们，这些成员发消息会被判为"不在群内"。
11. **系统账号 `uid = 1` 没有占用保护**：服务端只是把 `1` 当系统 id 使用，注册/数据库侧若把 1 分配给真实用户，会与系统消息混淆。
